❯ I'd like to configure my Android cell phone and Ubuntu 24 laptop so that the telephone audio from
  the phone can be routed through an AI model for speech-to-text transcription.  How can i do this?

● Three viable paths; the right one depends on whether you need real-time and whether you control
  both ends of the call.

  **1. Bluetooth HFP (best real-time path)** — Pair the phone to the laptop, then when a call comes
  in, route audio to the laptop instead of the phone earpiece. PipeWire on Ubuntu 24 exposes the HFP
  link as both a sink (your mic to remote) and a source (remote + sidetone to you). You capture the
  source with `parec` or `pw-record` and pipe to a transcriber. Caveats: HFP is mono 8 kHz (mSBC
  pushes it to 16 kHz wideband if both ends support it); both sides come mixed on one channel; you
  need `bluez` + `wireplumber` with HFP enabled (not the default A2DP-only profile — you toggle it
  via `pactl set-card-profile bluez_card.XX_XX... handsfree_head_unit`).

  **2. 3.5mm splitter / USB-C audio tap (most reliable, not real-time-friendly)** — Hardware
  splitter from the phone's headset output into the laptop's line-in. Captures the mixed call audio
  cleanly without OS cooperation. Works on any phone, ignores Android's recording restrictions, but
  you lose hands-free use unless you add a headset on the splitter's other branch.

  **3. On-device recorder + batch transcribe** — Google Phone's built-in recorder (regional) or an
  accessibility-service recorder app, then rsync/Syncthing the WAV to the laptop. Not real-time;
  modern Android (10+) blocks most third-party call recorders unless they exploit
  accessibility-service loopholes that Google keeps closing.

  **Transcription side on Ubuntu** is the easy half. Run `whisper.cpp` (or `faster-whisper` for GPU)
  locally, or pipe to OpenAI's Whisper API. Pipeline:

  ```
  parec --device=<bt-source> --rate=16000 --channels=1 --format=s16le \
    | ffmpeg -f s16le -ar 16000 -ac 1 -i - -f wav - \
    | whisper-stream  # or chunked POST to API
  ```

  For streaming-quality results, `whisper.cpp`'s `stream` example does VAD-chunked transcription on
  a rolling buffer; that's the closest to live captions you'll get without a paid streaming ASR
  (Deepgram, AssemblyAI Realtime, Azure Speech).

  **Recommendation:** Bluetooth HFP + local `whisper.cpp` streaming. It's free, on-device, and the
  HFP plumbing already works on Ubuntu 24's PipeWire stack.

  **Legal note:** Call-recording consent law varies (one-party vs all-party) by jurisdiction — worth
  checking before routing the remote party's audio through any pipeline, especially a cloud API.

  ### 2. Laptop: capture-and-stream bridge (`bridge.py`)

  ```python
  #!/usr/bin/env python3
  """Capture HFP source on laptop, stream 16 kHz s16le mono to pony,
     print transcripts received on the same socket."""
  import socket, subprocess, threading, sys

  PONY = ("pony", 9101)
  BT_SOURCE = "bluez_input.XX_XX_XX_XX_XX_XX.handsfree-head-unit"
  CHUNK = 3200  # 100 ms @ 16 kHz s16 mono

  sock = socket.create_connection(PONY)
  sock_w = sock.makefile("wb")
  sock_r = sock.makefile("r")

  # Reader thread: print transcripts (newline-delimited JSON or plain text)
  def reader():
      for line in sock_r:
          sys.stdout.write(line); sys.stdout.flush()
  threading.Thread(target=reader, daemon=True).start()

  # Capture from PipeWire BT source, pipe raw PCM to socket
  rec = subprocess.Popen([
      "pw-record",
      "--target", BT_SOURCE,
      "--rate", "16000", "--channels", "1", "--format", "s16",
      "-",
  ], stdout=subprocess.PIPE)

  while chunk := rec.stdout.read(CHUNK):
      sock_w.write(chunk); sock_w.flush()
  ```

  Run during a call:

  ### 3. Pony: streaming Parakeet server (`asr_server.py`)

  ```python
  #!/usr/bin/env python3
  """TCP server: read 16 kHz s16le PCM, run Parakeet cache-aware streaming,
     write newline-delimited transcripts back."""
  import socket, threading, numpy as np, torch
  import nemo.collections.asr as nemo_asr
  from nemo.collections.asr.parts.utils.streaming_utils import CacheAwareStreamingAudioBuffer

  MODEL = "nvidia/parakeet-tdt-0.6b-v2"
  PORT = 9101
  CHUNK_MS = 480   # encoder lookahead window for v2

  asr = nemo_asr.models.ASRModel.from_pretrained(MODEL).cuda().eval()
  asr.encoder.setup_streaming_params(
      chunk_size=int(CHUNK_MS * 16),  # samples
      shift_size=int(CHUNK_MS * 16),
      left_chunks=4,                   # 4 chunks of past context
  )

  def serve(conn):
      buf = CacheAwareStreamingAudioBuffer(model=asr)
      cache = asr.encoder.get_initial_cache_state(batch_size=1)
      pending = b""
      SAMPLES_PER_CHUNK = int(CHUNK_MS * 16)
      BYTES_PER_CHUNK = SAMPLES_PER_CHUNK * 2
      with conn, conn.makefile("wb") as out:
          while True:
              data = conn.recv(8192)
              if not data: break
              pending += data
              while len(pending) >= BYTES_PER_CHUNK:
                  chunk = np.frombuffer(pending[:BYTES_PER_CHUNK], np.int16).astype(np.float32) /
  32768.0
                  pending = pending[BYTES_PER_CHUNK:]
                  with torch.inference_mode():
                      text, cache = asr.transcribe_streaming(
                          audio=torch.from_numpy(chunk).unsqueeze(0).cuda(),
                          cache=cache,
                      )
                  if text.strip():
                      out.write((text + "\n").encode()); out.flush()

  srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
  srv.bind(("0.0.0.0", PORT)); srv.listen(1)
  print(f"asr_server listening on :{PORT}")
  while True:
      conn, _ = srv.accept()
      threading.Thread(target=serve, args=(conn,), daemon=True).start()
  ```

  NeMo's actual streaming API has a few variants per model class — the `transcribe_streaming` call

  ```
  # ~/.config/wireplumber/wireplumber.conf.d/60-bt-asr-route.conf
  ```

  ### Tradeoffs vs. the Python bridge

  **Wins:** no bridge process to start/restart; auto-link on HFP connect; PipeWire handles
  resampling/format negotiation; one less codebase.

  **Losses:** more state spread across config files (laptop + pony + WirePlumber); debug story is
  `pw-top` / `pactl list` instead of `print()`; the LAN-anonymous PulseAudio TCP listener is a small
  security surface (mitigate with `pulse.acl` if needed).

  For a project that's going to live for a while, the WirePlumber path is the right one. For a
  "prove the concept this weekend" prototype, the Python bridge is fewer moving parts. Either is
  fine — and if you start with the Python bridge, swapping in the tunnel later is a drop-in
  replacement (just retarget `parec` on pony, the asr_server doesn't care where its bytes come
  from).

❯ there's no BT option for speaker-only?

● No, unfortunately. The Bluetooth profile that carries phone-call audio is HFP (Hands-Free Profile,
  or its older sibling HSP) and the spec requires bidirectional audio — there is no "speaker-only"
  call profile in stock Bluetooth. A2DP *is* speaker-only, but Android specifically refuses to route
  call audio over A2DP because A2DP isn't designed for two-way real-time voice. So whichever way you
  slice it, the moment Android sends call audio to a BT device, that device is also expected to
  provide a mic.

  There's a future-tech answer: **Bluetooth LE Audio** (BT 5.2+ with LC3 codec) defines a
  unidirectional "Broadcast Audio Stream" mode that *could* support speaker-only call playback, and
  Android 13+ supports LE Audio for telephony. But pony's BCM20702 is BT 4.0+LE — not LE Audio — so
  this isn't a path you can take today without new hardware on both ends.

  There is one cheeky-but-clean workaround if you really want to avoid plugging a mic in: **pair
  pony as A2DP-only** (mask the HFP/HSP profiles in bluez). Android will see pony as a "music"
  device and won't route calls to it at all. Then for a call, you use the phone's normal
  speakerphone (the phone's own loud speaker), and a *separate* path handles transcription — e.g., a
  USB lavalier on pony aimed at the phone, or a screen-recorder-style accessibility app on Android
  that captures call audio and streams it to pony over WiFi/network. That avoids the BT-HFP-mic
  dilemma entirely, but it gives up the clean "phone routes to pony's speakers" UX you wanted.

  So the practical landscape really is: HFP with a mic on pony (any 3.5mm mic works), or accept
  silence upstream, or step outside BT for the audio path.

  **The structural problem:** since Android 10, the platform deliberately isolates voice-call audio
  from third-party apps. The `AudioPlaybackCapture` API (the one apps like scrcpy 2.x, SoundWire,
  AudioRelay use to stream phone audio to a PC over WiFi) explicitly excludes `STREAM_VOICE_CALL`
  and `USAGE_VOICE_COMMUNICATION`. The system Phone app doesn't opt in to capture, and there's no
  way for a third-party app to override that. This was tightened in 11, 12, 13, 14 in turn — Google
  views call-audio capture as a surveillance/malware vector.

  **The category of apps that try anyway:**

  - **Cube ACR** (formerly "Call Recorder - ACR") — best-known call recorder. Uses Accessibility
  Service tricks that *sometimes* work depending on phone vendor and Android version. Records to a
  file; doesn't stream live.

  device-specific implementations. Same file-based output model.
  - **OkCallRecorder**, **Truecaller's recorder** — same general category.
  - **scrcpy / SoundWire / AudioRelay** — won't help because their capture path explicitly excludes

  growing file to pony. A research project.

  HAL directly and capture `VOICE_CALL` stream as PCM, stream it over WiFi, all live. But rooting
  modern Android is increasingly painful (SafetyNet/Play Integrity blocks banking apps, etc.) and
  not worth it for one feature.

  **Specific to your stack:** if your incoming calls are ever coming over a VoIP app (Signal,
  WhatsApp, Google Voice, Linphone) rather than the cellular stack, you have *more* options because

  over VoIP.

❯ what's linger?

● Short version: a systemd feature that keeps a user's services running when they're not logged in.

  By default on systemd Linux, when you log out, your user's systemd instance (`user@UID.service`)
  shuts down — and that takes everything it owns with it: tmux servers, pipewire, cron jobs,
  anything. That's what just happened: claude's last ssh session ended, the user manager timed out,
  and the tmux server holding the Parakeet download got killed.

  `loginctl enable-linger <user>` flips a switch that says "run this user's systemd manager at boot,
  keep it running regardless of login state." With linger on:

  - The user has services running 24/7 even with nobody logged in
  - Tmux sessions, daemons, downloads, etc. survive logouts
  - Systemd-user timers fire on schedule

  Earlier I enabled linger for claude (so pipewire would run for the BT setup), then disabled it
  later (when we wanted cosine to own the audio device cleanly without claude's pipewire
  respawning). The disable is what caused the download to die when I logged out.

  For long-running unattended work on pony — model downloads, eventual ASR server, anything you want
  to keep running across reboots — linger is what you want. It's per-user, set once, persists.

  Reasonable plan: re-enable linger for claude, restart the download (Whisper this time), and now
  anything we kick off in claude's tmux survives. Pipewire stays masked so it won't fight cosine for

  ```bash
  # Foreground: emit marker
  marker="SID_$(openssl rand -hex 8)"; echo "$marker"
  ```

  (replacing `<MARKER>` with the value just emitted):

  ```bash
  until id=$(find ~/.claude/projects/-home-claude/ -maxdepth 1 -name '*.jsonl' \
                -mmin -2 -exec grep -l "<MARKER>" {} + 2>/dev/null | head -1); \
        [ -n "$id" ]; do sleep 2; done
  basename "$id" .jsonl
  ```

  The bash run ID lets you check the output later via `BashOutput`.
