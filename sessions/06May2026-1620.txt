❯ what's cuBLAS+cuDNN?

● Quick definitions:

  - **cuBLAS** — NVIDIA's CUDA BLAS library. BLAS = Basic Linear Algebra Subprograms (matrix
  multiply, vector add, dot product, etc.). It's the GPU-side equivalent of Intel MKL or OpenBLAS —
  every framework that does heavy linear algebra on NVIDIA GPUs eventually calls into cuBLAS for the
  inner loops.

  - **cuDNN** — NVIDIA's CUDA Deep Neural Network library. Hand-tuned GPU kernels for the operations
  specific to neural nets: 2D/3D convolutions, attention, RNN cells, batch normalization, softmax,
  etc. Things that *could* be expressed as a pile of cuBLAS calls but are dramatically faster as
  fused kernels.

  They're closed-source NVIDIA libraries, shipped as `.so` files. Anything that runs a neural net on
  an NVIDIA GPU — PyTorch, TensorFlow, ONNX Runtime, ctranslate2, NeMo, llama.cpp's CUDA backend —
  links against them at runtime.

  The reason we hit this: pony has the **driver** installed (the kernel module that actually talks
  to the GPU), but the **userspace libraries** are a separate install. The driver alone is enough
  for `nvidia-smi` to print stats, but not enough to run a model. NVIDIA distributes them three
  ways: the CUDA toolkit (system-wide), Conda packages, or pip wheels (`nvidia-cublas-cu12`,
  `nvidia-cudnn-cu12`) that drop the .so files into a venv's site-packages. We picked the pip route
  because it stays scoped to `~/asr-env/` instead of touching /usr/local.

❯ what is ctranslate2?

● CTranslate2 is a C++ inference engine for Transformer models, originally from the OpenNMT project
  (Systran's open-source MT lineage). It specializes in **fast, memory-efficient inference** — does
  its own quantization (int8, int8_float16, float16), graph optimization, and batching, with both
  CPU and CUDA backends. It competes with PyTorch for the inference half of a model's life: same
  model weights, but typically 2-4× faster and with smaller memory footprint, especially on CPU.

  It's used here because:

  - **`faster-whisper` is a thin Python wrapper around CTranslate2** that runs OpenAI's Whisper
  through it instead of PyTorch. The model we downloaded (`Systran/faster-whisper-large-v3`) is just
  OpenAI's whisper-large-v3 weights pre-converted to CTranslate2's format.
  - It supports a useful set of model families for our pipeline: Whisper, MarianMT (the
  `opus-mt-es-en` translator we downloaded), NLLB, M2M-100, plus various LLMs.
  - It uses **cuBLAS + cuDNN** for the heavy ops on GPU — that's why our missing-CUDA-libs error
  came from `ctranslate2` rather than from `faster_whisper` itself. CTranslate2 4.x is built against
  CUDA 12 specifically, which is why we couldn't use NVIDIA's 2604 repo (CUDA 13 only).

  Compare to NeMo (which Canary uses): NeMo runs on PyTorch, with its own optimization stack on top.
  So our pipeline ends up with two GPU runtimes side by side — CTranslate2 for Whisper+Marian,
  PyTorch+NeMo for Canary.

❯ we need the CUDA libraries for canary, too?

● Good question, and honestly: **no, not for Canary specifically**.

  PyTorch wheels from pytorch.org bundle their own CUDA libraries inside `site-packages/torch/lib/`
  — `libcublas.so.12`, `libcudnn.so.9`, `libcufft.so.11`, etc., all included. PyTorch loads them via
  its own dlopen logic and ignores the system ones. So Canary would run on a box with zero system
  CUDA libs as long as the NVIDIA *driver* is present (which it is — that's what `nvidia-smi`
  prints).

  The system-wide install benefits:

  - **ctranslate2 (faster-whisper path)** — does *not* bundle CUDA, looks it up on the system loader
  path. This is why our smoke test failed.
  - Future GPU build-from-source work on pony (compiling llama.cpp, vllm, custom CUDA kernels,
  anything using `nvcc`).

  So if we only cared about Canary we'd be skipping this apt install entirely. But the
  faster-whisper path was the one we picked first because it's lighter-weight (CTranslate2 stack vs
  PyTorch+NeMo stack), and pony is going to need full CUDA eventually for other GPU work, so it's
  worth doing once.

  Side effect of doing it system-wide: torch's bundled libs duplicate the system ones (~2 GB of
  redundancy living inside the venv). Annoying but harmless — torch always uses its bundles, so they
  don't fight.

❯ and ollama doesn't need the cuda libraries, or what?

● Right, ollama is the same pattern as PyTorch — **bundles its own CUDA runtime**, doesn't touch
  system libs.

  When you `curl -fsSL https://ollama.com/install.sh | sh`, the installer drops the CUDA libraries
  alongside the ollama binary in `/usr/local/lib/ollama/cuda_v12/` (or `cuda_v11/` for older GPUs).
  Ollama's Go runtime detects the GPU at startup, dlopen's the bundled `.so` files, and never looks
  at the system loader path. That's why ollama has worked fine on pony all along despite no system
  CUDA install — and why our local-inference setup with qwen3.6 on pony has been running happily.

  The "self-contained CUDA" pattern is the modern norm for shipped ML binaries. ctranslate2 is the
  unusual one — it deliberately depends on system libs to keep the wheel small (a torch wheel is ~2
  GB; the ctranslate2 wheel is ~50 MB precisely because it doesn't bundle CUDA).

  | Tool | CUDA approach |

❯ isolated practice tracks

● For piano practice tracks specifically, you want **HTDemucs 6-stem** (`htdemucs_6s`) — it splits
  into vocals/drums/bass/guitar/**piano**/other. The 4-stem variant lumps piano into "other" with
  strings, brass, etc., which is useless for your case.

  The killer-feature workflow for practice: demucs has a `--two-stems STEM` mode that produces *just
  two files* — the named stem isolated, and everything-else-minus-that-stem. So:

  ```
  demucs --model htdemucs_6s --two-stems piano song.mp3
  ```

  …gives you `piano.wav` (to learn the part by ear) and `no_piano.wav` (music-minus-piano backing
  track to play along with). Exactly the pair a pianist wants.

  **Quality reality check:** The 6-stem model is meaningfully *worse* than the 4-stem on its
  individual categories. Piano in particular is hard to separate cleanly because (a) it shares
  harmonic territory with vocals, (b) training data labeled "piano" is sparser than "vocals".
  Expect:
  - **Strong-piano genres** (Elton John, Billy Joel, Alicia Keys, jazz piano trios, Joni Mitchell) —
  works well.
  - **Textural/pad piano** in dense pop/rock mixes — bleed-through, residual ghost notes, sometimes
  the model just gives up and routes piano to "other".
  - **Solo piano works** — don't separate, just use the recording.

  **For your usecase, two practical alternatives worth considering:**

  1. **Moises.ai** (~$5/mo) and **LALAL.AI** (per-track credits) are commercial cloud services that
  run RoFormer-class models with proprietary fine-tunes. Quality is genuinely better than open
  htdemucs_6s for piano specifically — they invested in dedicated piano-separation training data. If
  practice-track quality is the priority and quantity is moderate, the cost is honestly competitive
  with paying for compute and your own time setting it up.

  2. **Local quality maximum** — clone `ZFTurbo/Music-Source-Separation-Training`, download a 6-stem
  RoFormer checkpoint trained for it. Better than htdemucs_6s but more setup friction. The 3090 will
  eat it for breakfast.

  Default I'd suggest: try `demucs --model htdemucs_6s --two-stems piano` on a few songs you
  actually want to practice, see if the quality is good enough. If it's mediocre on textural pieces
  but fine on the keyboardy ones, that's normal and probably acceptable for practice. If it's bad
  across the board, jump to RoFormer or Moises.

● Yes — but it's a trade-off, because Whisper is fundamentally an **offline model**: it expects a
  complete 30-second chunk and re-encodes from scratch every time, so it has no native concept of
  "partial transcription." There are three real options:

  **1. Just lower the VAD silence threshold.** Smallest change — drop `min_silence_duration_ms` from
  500 to 200. Snappier perceived response between utterances, but still emits one chunk at a time.
  Doesn't actually emit text mid-utterance.

  **2. Sliding-window streaming (the standard Whisper-streaming trick).** Every ~1 sec while speech
  is ongoing, re-transcribe the audio collected so far, and emit text. Catch: each re-transcription
  may *change* what was said earlier as more context arrives — Whisper's decoder is non-causal. The
  polished version of this is **Local Agreement-2** (Macháček et al., 2023): only commit text that
  two consecutive transcriptions agree on; the unstable tail gets reprinted each cycle. Result: text
  appears within 1-2 sec of being spoken, occasionally back-corrects. There's a `whisper_streaming`
  package or I can write it inline (~100 lines). Encoder pass on 5-10 sec audio takes ~150-300 ms on
  the 3090 — fits in a 1 sec loop.

  **3. Switch to a streaming-native model.** Whisper wasn't designed for this; **NVIDIA
  Parakeet-TDT** and similar RNN-T models *were*. They emit tokens per audio frame with ~200 ms
  latency, no re-transcription needed. Catch: Parakeet-TDT-0.6b-v2 (the model we abandoned
  mid-download yesterday because of the multilingual requirement) is **English-only**. Multilingual
  streaming-native ASR exists but is mostly behind cloud APIs (AssemblyAI, Riva). Canary's streaming
  variant exists but is heavier.

❯ what's "Silero VAD"?

● **VAD = Voice Activity Detection** — the task of deciding "is there speech here?" frame-by-frame
  on a stream of audio. **Silero VAD** is the small neural network that does this, from a research
  group called Silero. It's effectively the de facto open-source standard since ~2021, having
  displaced the older WebRTC VAD in most modern speech pipelines.

  What's special about it:

  - **Tiny.** ~2 MB ONNX model. Loads in under a second on CPU. Inference is ~5 ms per frame on a
  single core.
  - **Multilingual & noise-robust.** Trained on a diverse multilingual dataset of speech vs
  non-speech (music, traffic, fan noise, silence, etc.). Generalizes well; rarely false-triggers on
  background sound the way WebRTC VAD does.
  - **Streaming-native API.** `VADIterator` takes one frame at a time and emits `{'start': ms}` /
  `{'end': ms}` events as utterances begin and end. No batching required.
  - **Strict frame size.** Requires exactly 512 samples per frame at 16 kHz (or 256 at 8 kHz, etc.,
  always a power-of-2 ratio). That's what the `VAD_FRAME_SAMPLES = 512` and `BYTES_PER_FRAME = 1024`
  constants in our streaming script enforce.

  Why we needed it: Whisper itself doesn't know where utterances begin or end — give it a 60-minute
  file and it'll still try to transcribe the whole thing as one giant sequence. To stream from a
  live mic you have to chunk the audio into "utterances" yourself, and a learned VAD is dramatically
  better at that than rule-based silence detection. Silero is also what `faster_whisper`'s
  `vad_filter=True` calls internally to suppress hallucinations on silent input — that's the same
  model we re-used in `~/asr-stream.py` directly via `silero-vad`.

  Tunable parameters in our setup:

  - `threshold=0.5` — default speech-probability threshold. Lower = catches whispers but more
  false-triggers on noise.
  - `min_silence_duration_ms=500` — silence required before declaring "end of utterance." This is
  the parameter you'd lower for snappier perceived response.
  - `speech_pad_ms=200` — include 200 ms of audio before/after detected speech, to avoid clipping
  the first/last consonant.

  Compare to the alternatives we didn't use:
  - **WebRTC VAD** — signal-processing rules, no ML. Faster than Silero but markedly less accurate;
  triggers on noise.
  - **pyannote/voice-activity-detection** — bigger model (~30 MB), more accurate, but overkill for
  our case and pulls torch.

❯ does canary also need VAD?

● Yes — for the same architectural reason Whisper does. Canary (`canary-1b-flash`, `canary-1b-v2`)
  is also an **offline encoder-decoder model**, designed for 30-second chunks. Same constraints:

  - Encoder ingests log-mel features over a window, not per-frame
  - It hallucinates on silence (less famously than Whisper but yes)
  - It has no concept of "utterance starts here / ends here" — that has to be supplied externally
  - For a continuous mic stream you need *something* to chunk it into utterances

  NeMo's tooling assumes this and ships VAD helpers. The standard pattern is identical to what we
  already have: Silero VAD finds the speech boundaries, then each detected utterance gets fed to the
  Canary model. So the streaming script architecture for Canary would mirror `~/asr-stream.py`
  almost exactly — only the model loading and inference call change.

  The exception, and the reason you might pick a different model entirely, is the
  **streaming-native** Parakeet variants:

  - **`parakeet_realtime_eou_120m-v1`** is the cleanest example: emits `<EOU>` tokens itself when it
  decides an utterance has ended. **No separate VAD.** That's why "EOU" is in the name. The model
  has its own learned end-of-utterance detector trained jointly with ASR.
  - **`multitalker-parakeet-streaming-0.6b-v1`** processes audio in a streaming buffer (~1 sec
  lookahead) and emits text continuously, with speaker diarization on top. No VAD chunking; the
  streaming inference loop is the entire pipeline.

  So: VAD is a property of how *Whisper / Canary / standard Parakeet TDT* are run, not a property of
  speech recognition in general. Streaming-native models built around that constraint don't need it.

❯ what's "uv"?

● **uv** is a Python package and project manager from **Astral** — the same group that makes `ruff`
  (the popular Python linter). Released late 2024, written in Rust, became the standard "modern pip
  replacement" through 2025.

  It deliberately tries to be a drop-in replacement for **pip + virtualenv + pyenv + pip-tools +
  poetry + pipx** all at once, in a single static binary. The pieces:

  | It replaces | With | Speedup |
  |---|---|---|
  | `pip install` | `uv pip install` | ~10-100× |
  | `python -m venv` | `uv venv` | ~5× |
  | `pyenv install 3.12` | `uv python install 3.12` | Much simpler |
  | `poetry add foo` | `uv add foo` | Faster + lockfile compatible |
  | `pipx install ruff` | `uv tool install ruff` | Same idea |

  Key technical bits:

  - **Static Rust binary, ~40 MB.** No Python interpreter needed to install or run uv itself —
  that's why it can manage Python installations cleanly (no chicken-and-egg).
  - **The Pythons it installs** come from the `python-build-standalone` project (Gregory Szorc's
  work) — fully relocatable, fully-featured CPython builds with no system dependencies. They go into
  `~/.local/share/uv/python/` and aren't tied to any system package manager.
  - **Caching is content-addressed and hard-linked** — installing the same package into 50 venvs
  uses the disk space of one.
  - **Resolution is parallel** — that's where most of the speed comes from vs. pip's serial
  dependency walking.

  In our specific situation, the killer feature is `uv python install 3.12`. Ubuntu 26.04 doesn't
  ship Python 3.12 anywhere apt can find it, but uv just downloads a self-contained CPython 3.12
  binary and drops it under `~/.local/share/uv/python/cpython-3.12.X-...`. Then `uv venv --python
  3.12` makes a venv pointing at that, and pip / NeMo can install into it normally.

  It's MIT/Apache-2 licensed and the de facto standard now in the Python community (replaced poetry
  as the most-recommended new-project tool over the course of 2025).

❯ is it like nvm for python?

● Sort of, but broader. nvm has one job — install and switch between Node versions. uv does that for
  Python *plus* several other jobs in the same binary.

  The closer one-to-one Python analogue to nvm is **pyenv** — purely a Python version manager
  (`pyenv install 3.12`, `.python-version` files, that's it). uv subsumes pyenv but also takes over
  the roles that npm/yarn, virtualenv, pipx, and poetry play in their respective ecosystems.

  A more honest analogy: **uv is to Python what `bun` is to JavaScript** — a Rust-rewritten
  "everything-in-one" tool that replaces a stack of legacy tools (pip + venv + pyenv + pipx +
  poetry) with a single fast static binary. The only thing it doesn't replace is the CPython runtime
  itself; bun by contrast is also a runtime (replaces Node), so even that analogy isn't perfect.

  So:
  - Like nvm: yes, in that it manages multiple Python interpreters side-by-side
  - Unlike nvm: it's *also* the package installer, the venv manager, the project tool, and the tool
  installer — those are separate tools in the Node world (npm/yarn, no built-in venv concept, etc.)

  ## First-run workflow

  The session ID is needed for the compaction and KG filenames but
  not for the report's filename. So:

  1. Kick off session-ID detection in the background.
  2. Write the report (no session ID needed for the path; use a
     placeholder for the `**Session:**` line).
  3. Wait for the session ID to arrive (if it hasn't already).
  4. Use the session ID to write the compaction and KG files.
  5. Backfill the placeholder in the report.

  ### Step 1 — kick off session-ID detection (background)

  The session ID isn't an env var. Detection works by emitting a
  random marker, waiting for it to flush to your session's `.jsonl`
  file, then grepping the project's session directory to find the
  match. The flush takes a few seconds, so do it in background.

  ```bash
  # Foreground: emit marker
  marker="SID_$(openssl rand -hex 8)"; echo "$marker"
  ```

  Then launch the poller via Bash with `run_in_background: true`
  (replacing `<MARKER>` with the value just emitted):

  ```bash
  until id=$(find ~/.claude/projects/-home-claude/ -maxdepth 1 -name '*.jsonl' \
                -mmin -2 -exec grep -l "<MARKER>" {} + 2>/dev/null | head -1); \
        [ -n "$id" ]; do sleep 2; done
  basename "$id" .jsonl
  ```

  The bash run ID lets you check the output later via `BashOutput`.

  ### Step 2 — write the report

  Follow `~/project/skills/write-a-report/SKILL.md` for the structure
  and style rules. Pick a `<slug>` for the file (`<topic>-report.md`,
  `<topic>-analysis.md`, etc.). Write to `~/project/docs/<slug>.md`.

  If `write-a-report` was invoked earlier in this session, skip the
  report and go straight to step 3.

  **Re-run detection.** If `~/project/docs/<slug>.md` already exists,
  follow write-a-report's "Re-running in the same session" rule —
  update the existing report rather than overwrite it. Verifying the
  match needs the session ID, so in this case wait for step 3 to
  complete before writing. (For the common fresh-report case, you can
  write immediately; just use `_(pending)_` for the `**Session:**`
  header line and backfill in step 5.)

  ### Step 3 — collect the session ID

  Read the bash run's output (`BashOutput`). If the loop has exited,
  you'll see the UUID; if it hasn't, wait briefly and check again.
