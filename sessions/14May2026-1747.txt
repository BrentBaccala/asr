❯ what about the return audio microphone pass?

● Good question, and it splits into two cases.

  **First — do you actually need a return path?** The compaction states the goal as "transfer an
  inbound phone call to pony over BT, then SSH in to run **transcription** on the BT audio." That's
  one-way: pony listens, the remote party hears nothing from pony. If that's still the use case, you
  don't need a return path at all and the simple TRS line-in cable from option A is enough.

  **If you do need return audio** (pony speaks → remote party hears), the cabled solution is
  workable but fiddlier:

  The phone's 3.5mm jack is a **TRRS combo headset jack** (CTIA pinout) — tip+ring = stereo out,
  second ring = ground, sleeve = mic. So one cable can carry both directions, but pony has them on
  three separate TRS jacks, so you need:

  1. **TRRS-to-2-TRS headset splitter** (common laptop accessory, ~$5). TRRS plug into the phone's
  jack; on pony's side it breaks out into two TRS plugs: one labeled "headphone" (the phone's audio
  out), one labeled "mic" (the path back to the phone).
  2. **"Headphone" plug → pony's blue line-in jack** (phone → pony, exactly as in option A).
  3. **"Mic" plug → pony's green line-out jack** (pony → phone, the return path).

  Two real gotchas on the return path:

  - **Level mismatch.** Pony's line-out is line-level (~1 Vrms). The phone's mic-in expects
  mic-level (millivolts). Plugging line straight into mic will badly clip and distort. You need
  either a passive **line-to-mic attenuator** (~40 dB pad, sometimes called a "ground-loop isolator
  with attenuator" or sold as a "line-to-mic level converter", ~$10–15) or run pony's output volume
  very low. The attenuator is more stable.
  - **Mic-detection quirks.** The phone uses impedance on the mic line to know "this is a headset,
  not just headphones, so route the mic." Most TRRS splitters get this right (mic line is tied to
  ground through the right impedance), but cheap ones occasionally don't and the phone treats it as
  headphones-only with no mic. If you go this route, get one with reviews specifically confirming
  the mic input works on Android.

  **Quality ceiling on the return path:** the phone's mic-input ADC is tuned for a headset condenser
  mic, ~16-bit/16 kHz mono. Fine for voice (good enough that the remote party will understand), but
  not high fidelity. That's a phone-side limit, not anything we can fix on pony.

  **Alternative if return-audio quality matters:** a small **USB-C audio adapter on the phone end**
  (USB-C DAC/ADC, $15-30) gives the phone a higher-quality analog interface. Same TRRS-and-splitter
  topology after that, but better ADC on the phone side. Probably overkill for ASR-style use.

  So: if it's transcription-only, just the line-in cable. If you need bidirectional, add a TRRS
  splitter + an attenuator on the return leg. Which case is it?

● Good design constraint. Here's the architecture that fits it:

  **The "works regardless of pony" property comes free if we use RTP instead of a TCP tunnel.** RTP
  is UDP fire-and-forget: samsung's PipeWire just emits packets; if pony's listening they arrive, if
  not they're discarded. No connection state to fail, no buffer to overflow, and crucially the *call
  audio path on samsung is independent of the RTP overlay* — so when pony is down, nothing about the
  call is degraded.

  PulseAudio's tunnel modules are TCP-based and would *not* satisfy this: a dead pony would put the
  tunnel sink into an error state and PipeWire's routing graph would notice.

  **Topology I'd recommend:**

  ```
  Phone <--HFP--> Samsung BT <--PipeWire--> Analog jack (headphones + mic)
                                    |
                                    +--monitor--> [RTP sink, stereo]
                                                    |
                                                    v
                                                  Pony [RTP source]
                                                    |
                                                    v
                                            Whisper streaming x2
                                            (L=remote party, R=you)
                                                    |
                                                    v
                                           Transcript stream
  ```

  Key trick: instead of tapping the dynamic bluez source/sink (which only exist while a call is
  active), tap the **persistent** analog playback monitor + analog capture. During a call, the
  playback monitor carries the remote party's voice (the HFP downlink that's being routed to
  headphones), and the analog capture carries your voice (which is then routed up to HFP). Both
  sources exist all the time, so the RTP stream is statically configurable at PipeWire startup and
  we don't have to chase profile transitions.

  Combine them into a single stereo RTP stream: left channel = playback monitor (remote), right
  channel = mic (you). Saves having two RTP streams to keep in sync.

  **Caveat with always-on streaming:** outside a call, the playback monitor catches music/system

❯ why does one pipewire process show 5 times as a client?

● Those five "pipewire" entries are all *internal* client connections inside the one pipewire daemon
  (pid 12817). PipeWire's architecture is uniform: every node you see in the graph — whether it's an
  external process talking PipeWire over a socket or an in-process module — registers via the same
  client/connection abstraction. So a module loaded into pipewire's own address space still opens a
  client connection to register the nodes it owns.

  Counting modules I added to your config:

  | Module | What it registers |
  |---|---|
  | `module-rtp-sink` × 2 | 2 RTP sinks (`rtp_call_remote`, `rtp_call_me`) |
  | `module-loopback` × 2 | 4 nodes total — each loopback exposes a capture node + a playback node |

  That's 4 modules, ~6 nodes, and most of those modules share a single client connection per module.
  With one or two additional default helpers PipeWire loads at startup, you end up at the 5 you're
  seeing — roughly one per module-I-added, plus pipewire's own internal protocol client.

  If you want to see exactly what each one is, `wpctl inspect 38` (etc.) will dump its properties —
  look for `module.id`, `client.api`, and `media.name`. You'll typically see entries like `module.id
  = 7 ; module.name = "libpipewire-module-rtp-sink"` matching them up to your config.

  It's not a leak or a duplication bug — each module needs its own "voice" on the bus to register
  the nodes it manages, and that registration looks like a client connection. The count would drop
  back to baseline if you removed the config.

  ## Tuning

  - Cold-start cost is ~120 s on every path (the bge-m3 query in `query.py` is the dominant cost,
  shared by all paths). Sonnet's agent loop (`--sonnet`) adds ~30–60 s of tool-call round-trips; a
  single ollama synthesis call (`--qwen` etc.) adds ~5–15 s once the model is hot, plus ~30–90 s
  cold-load on a 3090; sonnet-shot (`--sonnet-shot`) adds ~10–20 s of one Anthropic round-trip.
  - `--all` is dominated by serial cold-loads on pony: only one ~15–18 GB model fits in the 24 GB
  3090 alongside bge-m3, so each ollama request after the first incurs an unload+reload (~30–90 s
  each). Wall is roughly `bge-m3 retrieval + sonnet wall + Σ (per-model cold load + generate)` ≈ 5–8
  min for a typical topic. The five `qwen-search.py` calls all fire in parallel from the skill's
  perspective; ollama's request queue serializes them.
  - The KG side is small (~48 entities). Most signal comes from chunks. If the topic is clearly
  "session-shaped" (a debugging arc, a port, a design decision), the report's lead bullets will be
  session entities; if the topic is "code-shaped" (a function, a file, a branch), commits will
  dominate.

  ## When not to use this

  - Mid-session pivots ("now let's also look at Y") — the user has context already.

  - A topic the user has *just* worked on (e.g. they opened a previous session moments ago on the
  same thing). The prior session's KG extraction won't have been drained yet, so a search will miss
  it.
  - When `~/lightrag-history/data/` doesn't exist or is empty (fresh-clone state). Tell the user the

  1. `pw-data-loop` was running at **RR 20** instead of FF 88.

  ### Step 1 — kick off session-ID detection (background)

  The session ID isn't an env var. Detection works by emitting a
  random marker, waiting for it to flush to a `.jsonl` file, then
  grepping the session directories to find the match. The flush takes
  a few seconds, so do it in background.

  Two locations need to be searched, because subagents log to a
  different place than top-level sessions:

  - **Top-level sessions** flush to
    `~/.claude/projects/<bucket>/<UUID>.jsonl`. The ID is the basename.
  - **Task-runner subagents** flush to
    `~/project/sessions/subagents/<parent>/agent-<aid>.jsonl`. The ID
    is the composite `<parent>-<aid>`.

  ```bash
  # Foreground: emit marker
  marker="SID_$(openssl rand -hex 8)"; echo "$marker"
  ```

  Then launch the poller via Bash with `run_in_background: true`
  (replacing `<MARKER>` with the value just emitted):

  ```bash
  until path=$( { \
          find ~/.claude/projects/ -maxdepth 2 -name '*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
          find ~/project/sessions/subagents/ -maxdepth 2 -name 'agent-*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
        } | head -1); \
        [ -n "$path" ]; do sleep 2; done
  # Translate path to session ID (subagent → composite, top-level → UUID)
  case "$path" in
    */subagents/*/agent-*.jsonl)
      parent=$(basename "$(dirname "$path")")
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      echo "${parent}-${aid}" ;;
    *) basename "$path" .jsonl ;;
  esac
  ```

  The bash run ID lets you check the output later via `BashOutput`.

  **Why the subagent search matters.** Before this dual-search, the
  poller only checked `~/.claude/projects/-home-claude/`. In subagent
  runs the marker never appeared there (subagent events go to the
  `sessions/subagents/` tree instead), the poller timed out, and the
  agent fell back to "find the recently-touched top-level JSONL" —
  which yielded the *parent session's* UUID, not the subagent's own
  identity. That accidentally produced a per-parent compaction
  filename, collapsing multiple subagents under one parent into the
  same file. The dual search yields the correct composite ID and gives
  each subagent its own compaction.

  ### Step 2 — write the report

  Follow `REPORT.md` (in this skill directory) for the structure and
  style rules. Pick a `<slug>` for the file (`<topic>-report.md`,
  `<topic>-analysis.md`, etc.). Write to `~/project/reports/<slug>.md`.

  If a report was already written earlier in this session (the
  findings doc the task was set up to produce), skip the report
  and go straight to step 3.

  **Re-run detection.** If `~/project/reports/<slug>.md` already
  exists, follow `REPORT.md`'s "Re-running in the same session" rule
  — update the existing report rather than overwrite it. Verifying
  the match needs the session ID, so in this case wait for step 3 to
  complete before writing. (For the common fresh-report case, you can
  write immediately; just use `_(pending)_` for the `**Session:**`
  header line and backfill in step 5.)

  ### Step 3 — collect the session ID

  Read the bash run's output (`BashOutput`). If the loop has exited,
  you'll see the UUID; if it hasn't, wait briefly and check again.
  Don't proceed past this step without a session ID.

  ### Step 4 — write the compaction and KG files

  #### Compaction summary (for a future Claude)

  Path: `~/project/compactions/session-<ID>.md`. Structure and content
  per `COMPACT.md` (in this skill directory) — progress-report half
  on top, `---`, then the `<analysis>` + `<summary>` blocks following
  `COMPACT_PROMPT.md` (also in this directory).

  If the file already exists, this is a re-run — overwrite with a
  cumulative summary covering the whole session through now (the
  reader is a future Claude; they only need the latest snapshot).

  You don't need to list the user's instructions verbatim — the full
  transcript is retrievable from the task runner or the session jsonl
  when needed. Capture the *essence* in section 1 of the compaction.

  #### Knowledge-graph entry (for the search engine)

  Path: `~/lightrag-history/incoming/session-<ID>.json`. Schema and
  per-field guidance per `~/lightrag-history/EXTRACT_PROMPT.md` (the
  canonical spec). Density and entity-type refinements per `KG.md`
  (in this skill directory) — tightens the bare EXTRACT_PROMPT
  defaults to encourage richer extraction (calibrate against the
  compaction's analysis block; include when hesitating; soft entity
  types like `pattern`, `failure-mode`, `constraint`, `gotcha` are
  first-class). Re-run handling per `KG.md`'s "Re-extracting in the
  same session" section — overwrite if still in `incoming/`,
  delta-style if already drained.

  **Coverage check before reporting paths.** Read the compaction
  `<analysis>` block you wrote in the previous sub-step. For each
  substantive technical concept named there (machines, files,
  patterns, decisions, failure modes, constraints, reports, …),
  confirm there's an entity for it in the KG. For each pair of
  concepts the session explicitly connected, confirm there's an
  edge. If you find gaps, add them before moving on. The failure
  mode this catches is "wrote a 22-concept compaction, then a
  7-entity KG" — where the compaction faithfully recorded the
  session but the KG silently lost most of the searchable material.
  Enumeration mismatch is the signal; numeric thresholds are not
  required.

  ### Step 5 — backfill the report's session ID

  If you wrote the report fresh in step 2 with a `_(pending)_`
  placeholder, edit `~/project/reports/<slug>.md` to replace it with
  the real `<ID>` (either a 36-char UUID for top-level sessions or
  the 54-char composite for subagents). Skip this step if the report
  was an in-place update (re-run case — already has the real ID) or
  was skipped entirely (a report was already written earlier in the

  ### Step 6 — commit the `~/project` changes

  The report(s) and compaction live in `~/project`; commit them so
  the session's debrief is preserved in git rather than left as
  loose working-tree edits the user has to chase down later. The KG
  file lives in `~/lightrag-history` (separate repo) — leave that
  to the user or a later commit step; this skill only handles

  ```bash

                            compactions/session-<ID>.md \

  Use a commit message that names what the session was about — not
