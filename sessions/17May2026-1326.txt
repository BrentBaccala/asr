❯ what's the difference between large-v3 and large-v3-turbo?

❯ let's do transcription for now.  are there any models that process audio by looking at overlapping
  chunks, say, 4 seconds of context, but shifted left every second or so, so it looks at several

● Good question — and the precise answer splits into two genuinely different things, because what
  you described is more a *decoding strategy* than a model property.

  ## (A) Sliding-window wrappers around an offline model (this is exactly your idea, applied to
  Whisper)

  Whisper itself has no streaming mode — it's a 30-second offline encoder-decoder. But your "4 s of
  context, shifted left ~1 s" scheme is a well-known wrapper technique, and there's a reference
  implementation: **`whisper_streaming`** (UFAL, Macháček et al., *"Turning Whisper into a Real-Time
  Transcription System"*). It does precisely what you're picturing, with one critical addition you'd
  otherwise have to invent:

  - It re-runs faster-whisper on an overlapping, sliding/growing buffer every ~1 s.
  - The trailing edge of each run is unstable (the model revises the last few words as more audio
  arrives), so you **cannot just print the latest run's text** — it flickers and rewords. The fix is
  a **LocalAgreement** policy: only *commit* a token once two successive overlapping runs agree on
  it. Unconfirmed tail stays provisional.

  Net effect: each emitted word still benefited from several seconds of left context (near-offline
  accuracy), latency granularity drops to ~1 s, but a word isn't *confirmed* until the next
  overlapping run sees it — so there's an inherent ~1-chunk confirmation lag, and you pay redundant
  recompute (re-running large-v3 on overlapping audio every second). On the 3090 that recompute is
  affordable. **`WhisperLive`** (Collabora) is a similar VAD+chunk streaming Whisper wrapper.

❯ if this loaded a model, does it stay loaded on the GPU if the command is run again within seconds?

● No. Each invocation is a brand-new Python process, and nothing about the model survives between
  processes.

  **What actually happens on each run:**
  - `ASRModel.from_pretrained(...)` reads the cached `.nemo`, builds the model graph, loads weights,
  then `.to("cuda")` uploads them into GPU VRAM and spins up a CUDA context. That's the ~8–10 s
  startup you see in every test.
  - When the process exits (Ctrl-C, EOF, crash), the CUDA context is torn down and that VRAM is
  freed immediately.
  - Run it again two seconds later → a fresh process repeats the entire load from scratch. There's
  no daemon, no shared cache, no GPU-resident persistence.

  **What a quick re-run *does* benefit from:** only the OS page cache. After the first load the
  `.nemo` file sits in RAM filesystem cache, so the *disk-read* part is fast. But that's a small
  slice — the ~8–10 s is dominated by framework init, model construction, and the CUDA
  upload/context setup, and that recurs every single time regardless of how recently it ran.

  **Within one run**, the model stays resident on the GPU for the life of the process — that's
  exactly why per-chunk transcribe is ~0.1–0.3 s and not paying a reload each chunk. The design
  intent is that you start it once and leave it running for the whole call/session, not restart it.

  **One caveat for "run again within seconds":** if you start it again *without killing the first
  one*, you get two independent processes each holding their own copy in VRAM (~2–3 GB model + ~1–2
  GB CUDA overhead each). The RTX 3090's 24 GB absorbs a couple of copies, but they're redundant and
  they'll contend for the GPU — and cosine's faster-whisper `asr-call-transcribe`, if also running,
  holds its own separate VRAM on top.

  If fast restarts actually matter to you — e.g., you want to relaunch with different flags without
  eating 10 s each time — the fix is a **persistent model server**: one long-lived process loads
  parakeet once and holds it on the GPU, and the stream scripts become thin clients that connect
  over a socket/FIFO and pay zero load time. That's a clean ~100-line addition (a server wrapper +
  making `stream-parakeet-buffered.py` able to talk to it). Want me to build that?

  ```bash
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
        } | head -1); \
        [ -n "$path" ]; do sleep 2; done
  # Translate path to session ID (subagent → composite, top-level → UUID)
  case "$path" in
    */subagents/*/agent-*.jsonl)
      parent=$(basename "$(dirname "$path")")
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      echo "${parent}-${aid}" ;;
    *) basename "$path" .jsonl ;;
  esac
  ```

  The bash run ID lets you check the output later via `BashOutput`.

  **Why the subagent search matters.** Before this dual-search, the
  poller only checked `~/.claude/projects/-home-claude/`. In subagent
  runs the marker never appeared there (subagent events go to the
  `sessions/subagents/` tree instead), the poller timed out, and the
  agent fell back to "find the recently-touched top-level JSONL" —
  which yielded the *parent session's* UUID, not the subagent's own
  identity. That accidentally produced a per-parent compaction
  filename, collapsing multiple subagents under one parent into the
  same file. The dual search yields the correct composite ID and gives
  each subagent its own compaction.
