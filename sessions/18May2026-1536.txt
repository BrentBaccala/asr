  # lightrag — search prior work for a topic (multi-backend)

  When invoked, the parent session:

  1. Tells the user in one sentence: *"Searching lightrag-history for prior work on `<TOPIC>` — back
  in ~2 min."*
  2. Picks the topic phrase from the user's opening message. Strip filler ("we're working on",
  "let's look at", "I want to debug"); keep the noun phrase. Examples:
     - `"we're working on lightrag"` → `lightrag`
     - `"let's look at the parallel-bba flake on c200-1"` → `parallel-bba flake on c200-1`
  3. Picks a backend mode from the args (default: `both`):
     - no flag, or `--both` → run sonnet AND qwen3.6 in parallel (the historic 2-model default)
     - `--sonnet` → sonnet only (agent loop with tools)
     - `--sonnet-shot` → single-shot Sonnet, **no tool use** (architecturally identical to ollama
  paths; only the model differs). Use this when comparing models head-to-head — it isolates the
  model effect from the agent-loop effect.
     - Single ollama model: `--qwen` (qwen3.6:27b), `--gemma3` (gemma3:27b), `--mistral-small`
  (mistral-small:24b), `--gpt-oss` (gpt-oss:20b), `--command-r` (command-r:35b)
     - `--all` → run sonnet AND all 5 ollama models in parallel (6 reports total). Pony's 24 GB 3090
  only fits one ~15–18 GB model + bge-m3 at a time, so ollama serializes the synthesis calls and
  swaps models in/out of VRAM — expect ~5–8 min wall. Tell the user the longer ETA up front instead
  of the usual ~2 min.
  4. **In the same response**, launches the chosen backend(s) in the background:
     - **Sonnet path** (`--sonnet`): a background `Agent` (`subagent_type: general-purpose`, `model:
  sonnet`) with the agent prompt below.
     - **Sonnet-shot path** (`--sonnet-shot`): two-step (the second step is the background launch):
       1. **Foreground**: capture the dated synthesis prompt by running
  `~/lightrag-history/scripts/qwen-search.py --prompt-only "<TOPIC>"` via Bash. Stdout is the
  fully-rendered prompt (instructions + dated hits JSON), ready to feed to a synthesis-only agent.
  **No LLM call happens at this step.**
       2. **Background**: launch an `Agent` with `subagent_type: synth-only` (defined at
  `~/.claude/agents/synth-only.md`, `tools: []`), `model: sonnet`, passing the captured prompt
  verbatim as the agent's `prompt` argument. The agent has no tools, so the only thing it can do is
  generate the markdown report from the supplied JSON.
     - **Ollama path** (any of `--qwen`, `--gemma3`, `--mistral-small`, `--gpt-oss`, `--command-r`):
  a background `Bash` call to `~/lightrag-history/scripts/qwen-search.py [--model NAME] "<TOPIC>"`.
  Map flag → model name:
       | flag | model |
       |---|---|
       | `--qwen` | `qwen3.6:27b` (script default — no `--model` arg needed) |
       | `--gemma3` | `gemma3:27b` |
       | `--mistral-small` | `mistral-small:24b` |
       | `--gpt-oss` | `gpt-oss:20b` |
       | `--command-r` | `command-r:35b` |
     - **`--all`**: launch sonnet (Agent) **plus all five ollama models** (five `Bash` calls to
  `qwen-search.py --model NAME`) in the same response. Six parallel background tasks total. Pony
  will swap models in/out of VRAM serially, so wall is dominated by the slowest cold-load chain.
  5. Waits for whichever it launched. When results return, classify before presenting:
     - **`both` mode, both succeeded with substantive content**: present sonnet's report under `##
  Sonnet`, qwen's under `## Qwen3.6`, then add a `## Comparison` section. Be HONEST — not
  diplomatic. Address each of:
       - **Coverage**: did they pick the same hits? Did one find dated material the other missed?
       - **Accuracy**: did either invent dates, source_ids, or file paths not in the underlying
  corpus? (Cross-check by spot-reading one or two cited files.)
       - **Template fidelity**: did either drift from the markdown structure (extra preamble,
  missing sections, wrong heading levels)?
       - **Useful judgment**: which would the user actually find more useful for *this* topic? Why?
  Don't both-sides it if one is clearly better.
     - **`both` mode, qwen failed** (script exited non-zero — pony down, ollama down, network
  flake): present sonnet's report under `## Result` plus a one-line note: `(qwen path unavailable —
  pony or ollama down; sonnet only.)`. Do NOT retry qwen; do NOT block.
     - **`both` mode, sonnet failed**: present qwen's report plus the same one-line fallback note
  (vice versa). Sonnet via API rarely fails for transient reasons; if it does, mention what the
  error was.
     - **`both` mode, asymmetric content** (both exited 0, but one returned substantive content
  while the other returned "No prior work found" or a near-empty report): treat the empty side as a
  likely backend bug, not a real "no prior work" signal. Present the substantive report under `##
  Result` plus a one-line note: `(qwen path returned "no prior work" while sonnet returned N hits —
  likely wrapper bug; investigating recommended)` (or the symmetric note if sonnet was the empty
  one). Do NOT silently average the two reports — an empty report next to a 8-bullet report on the
  same topic is almost always wrapper failure, not a real signal. The threshold for "asymmetric":
  one side has zero `Recent work` bullets and the other has three or more.
     - **`--all` mode**: present each successful report under its own model heading: `## Sonnet`,
  `## Qwen3.6:27b`, `## Gemma3:27b`, `## Mistral-Small:24b`, `## GPT-OSS:20b`, `## Command-R:35b`

     - **Single-backend mode** (`--sonnet`, `--sonnet-shot`, or any single `--<ollama>` flag):
  present the one report under `## Result`.
  6. Read any files suggested in the `Where to read more` section of whichever report you trust
  most.
  7. Proceed with whatever the user actually asked for next.

  Multi-topic queries (X and Y): launch the chosen backend(s) per topic. With default `both` and two

  ## Sonnet agent prompt

  ```
  You are searching the ~/lightrag-history LightRAG 1.4.15 index for prior work on a specific topic.
  The index has ~6260 chunks (commit messages, session summaries, progress reports, task docs, task
  prompts) plus a small KG (~48 entities, ~58 edges). Return a recency-ranked markdown report —
  nothing else.

  ## Topic

  <TOPIC>

  ## Step 1 — Search

  Run from the venv (the script's shebang already points at it):

      ~/lightrag-history/scripts/query.py "<TOPIC>" --mode mix

  No --summary-only — we want full chunk content for date extraction. Expect ~120 s wall (cold
  start, 2 embedding workers + naive/local/global passes). Output has three sections: entities,
  relationships, chunks. Each chunk has a `source_id` and content.

  If the run errors or times out, abort and return only:

      No usable results — the search errored: <one-line cause>.

  ## Step 2 — Extract dates

  For each hit, get a defensible date:

  - **Commit chunks** (`source_id` = `<repo>:<short-sha>`): parse `Date: YYYY-MM-DD` from the
  content body.
  - **Legacy session entities** (`session-YYYYMMDD-HHMM`): parse from the name.
  - **UUID session entities** (`session-<UUID>`): read
  `~/lightrag-history/processed/session-<UUID>.json` and use `source.created_at`. Fall back to file
  mtime if the field is missing.
  - **Progress-report chunks and legacy compaction chunks** (`source_id` =
  `progress-report:DDMonYYYY-HHMM` or `compaction:DDMonYYYY-HHMM`): parse the date from the
  source_id.
  - **Session-named compaction chunks** (`source_id` = `compaction:session-<UUID>`): the date isn't
  in the source_id. Use the file mtime (`stat -c %y ~/project/compactions/session-<UUID>.md`) — it
  corresponds to when `/end` last wrote the file for this session, which is what you want.
  - **Task-doc / task-prompt chunks** (`source_id` = `task-doc:<slug>` or `task-prompt:<slug>`):
  usually undated in content. Run `git -C ~/project log -1 --format=%ai -- docs/<slug>.md` (or
  `prompts/<slug>`) and use the commit date. If still no date, omit the hit.

  If a hit lacks a date you can defend, omit it rather than guess.

  ## Step 3 — Synthesize

  Output exactly this structure (omit any section with no content). Target ~250 words; hard cap 400.

  ```
  ## What we know about <TOPIC>

  One sentence summarizing the topic as it appears in the index. If the search returned nothing
  on-topic (all chunks are clearly fuzzy matches on a single shared word), say "No prior work found
  in the lightrag-history index on <TOPIC>." and stop.

  ## Recent work (most recent first)

  Up to 8 bullets:
  - **YYYY-MM-DD** — one-sentence summary. _[source_id]_

  Prefer compactions, session entities, and progress reports over individual commits — they're
  denser. Compactions in particular are the richest source: they bundle a progress report, a
  chronological analysis, and a full conversation summary for one session, so a single hit often
  answers the topic on its own. Merge multiple hits describing the same work into one bullet (pick
  the highest-relevance source_id). Include commits when they're the only evidence.

  ## Open threads

  Bullets for anything explicitly pending, blocked, deferred, or marked TODO in the hits. Skip the
  section entirely if none.

  ## Where to read more

  2-3 file paths (under `~/lightrag-history/processed/`, `~/project/compactions/`,
  `~/project/reports/`, `~/project/docs/`, or `~/project/progress-reports/`) ranked by relevance.
  Do not include directory names like `~/project/progress-reports/`; name only specific files.  If
  there's a recent compaction, be sure to include it.
  ```

  ## Output rules

  - Return only the markdown report. No preamble, no sign-off, no narration of process.
  - Do not invent dates, source_ids, or file paths. If you can't verify it, omit it.
  - If `query.py` returns plenty of hits but none are on-topic, that's a "No prior work found" — say
  so and stop. Better empty than padded.
  ```

  ## Sonnet-shot path notes

  The `--sonnet-shot` path is architecturally identical to the ollama paths
  (deterministic Python date extraction + single synthesis call) — the only
  difference is which model produces the synthesis. This is the right path
  when answering "is sonnet's win in `--sonnet` mode coming from the model
  or from the agent loop's tool-based verification?"

  How it runs:
  - The skill captures the fully-rendered synthesis prompt by calling
    `qwen-search.py --prompt-only "<TOPIC>"`. That flag does Steps 1–2
    (query + date extraction) but emits the prompt instead of calling
    ollama. Single source of truth — same prompt, same dated hits, as
    every ollama path.
  - The captured prompt goes to a synth-only Agent (`tools: []`) so no
    tool-loop is possible even by accident.

  Failure modes:
  - `qwen-search.py --prompt-only` shares its exit codes 0/2 with the
    full path — 2 means the corpus query failed and `--sonnet-shot` is
    also unavailable for this topic. Codes 3/4 cannot fire (no ollama
    call).
  - The Agent itself can fail by API error — surface it the same way as
    the regular `--sonnet` path.

  ## Ollama path notes

  The ollama path is implemented in `~/lightrag-history/scripts/qwen-search.py` (name kept for
  backward compat — the script itself is model-agnostic):

  - Runs `query.py "<TOPIC>" --mode mix`.
  - Deterministically derives a date for each hit from its `source_id` pattern (the same rules from
  the sonnet prompt's Step 2, but in Python — no LLM tool calls).
  - Sends one synthesis-only call to the chosen model on pony's ollama (`http://192.168.0.142:11434`
  by default). Model is selected via `--model NAME` (default `qwen3.6:27b`).
  - Prints the resulting markdown report on stdout.

  Models currently available on pony (from `ssh pony ollama list`): `qwen3.6:27b`, `gemma3:27b`,
  `mistral-small:24b`, `gpt-oss:20b`, `command-r:35b`. The skill maps each `--<flag>` to one of
  these (see step 4 table). Adding a new model later is a one-line addition there plus an optional
  sampling preset in `qwen-search.py`'s `MODEL_PRESETS` dict (the script falls back to ollama's
  per-model defaults if no preset is registered, so it works out of the box).

  Env overrides if pony moves IPs or the default model is changed:
  - `OLLAMA_HOST` (default `http://192.168.0.142:11434`)
  - `QWEN_MODEL` (default `qwen3.6:27b`; `--model` arg wins over env)

  Exit codes the skill should distinguish:
  - `0` → success, stdout is the markdown report.
  - `2` → query.py / parsing failed (lightrag corpus issue — sonnet probably also fails).
  - `3` → ollama unreachable (pony down). Treat as "ollama path unavailable, fall back to sonnet."
  - `4` → unexpected ollama response shape (model returned malformed JSON). Surface this as
  `(<model> returned unparseable output)` in the comparison section, but still show the sonnet
  result.

  ## Tuning

  - Cold-start cost is ~120 s on every path (the bge-m3 query in `query.py` is the dominant cost,
  shared by all paths). Sonnet's agent loop (`--sonnet`) adds ~30–60 s of tool-call round-trips; a
  single ollama synthesis call (`--qwen` etc.) adds ~5–15 s once the model is hot, plus ~30–90 s
  cold-load on a 3090; sonnet-shot (`--sonnet-shot`) adds ~10–20 s of one Anthropic round-trip.
  - `--all` is dominated by serial cold-loads on pony: only one ~15–18 GB model fits in the 24 GB
  3090 alongside bge-m3, so each ollama request after the first incurs an unload+reload (~30–90 s
  each). Wall is roughly `bge-m3 retrieval + sonnet wall + Σ (per-model cold load + generate)` ≈ 5–8
  min for a typical topic. The five `qwen-search.py` calls all fire in parallel from the skill's
  perspective; ollama's request queue serializes them.
  - The KG side is small (~48 entities). Most signal comes from chunks. If the topic is clearly
  "session-shaped" (a debugging arc, a port, a design decision), the report's lead bullets will be
  session entities; if the topic is "code-shaped" (a function, a file, a branch), commits will
  dominate.

  ## When not to use this

  - Mid-session pivots ("now let's also look at Y") — the user has context already.
  - Trivial openers — `/loop`, `/end`, `continue task N`, "hi", "what time is it".
  - A topic the user has *just* worked on (e.g. they opened a previous session moments ago on the
  same thing). The prior session's KG extraction won't have been drained yet, so a search will miss
  it.
  - When `~/lightrag-history/data/` doesn't exist or is empty (fresh-clone state). Tell the user the
  index isn't populated and skip.

❯ what's "greedy + modified-beam"?

● They're the two decoding strategies for the RNN-T transducer at inference — how the model turns
  encoder output into a token sequence. You saw both in bookbot's repo (`streaming/greedy_search/`,
  `streaming/modified_beam_search/`), each with its own published WER.

  **Why a transducer even needs a "method":** at each frame an RNN-T decides *emit a token* or *emit
  blank (advance)*, and tokens depend on previously emitted tokens. So decoding is a search over
  alignments, not a per-frame argmax. How you do that search trades latency for accuracy.

  **greedy_search** — at every step take the single highest-probability choice, keep no
  alternatives. Purely local, frame-synchronous, cheapest, lowest latency. The cost: one early wrong
  token can't be undone. This is what you actually run live — our `stream-sherpa-ipa.py` passes
  `decoding_method="greedy_search"`.

  **modified_beam_search** — keep the top-N hypotheses (a beam; `num_active_paths`, bookbot used 4),
  expand them in parallel, prune to N each step. Because alternatives are retained, a
  locally-suboptimal token can still win if later context favors it → more accurate. "Modified" =
  icefall's transducer-specific simplification (≈ one emission per frame per hypothesis) that makes
  beam search fast and parallelizable while keeping most of the accuracy gain. Costs more compute
  and adds latency vs greedy, but it's still streaming-compatible.

  (There's also **fast_beam_search** — a k2 FSA/graph-constrained beam, the third dir in bookbot's
  repo. Not needed for the plan; greedy + modified-beam bracket the practical range.)

  **Why the plan evaluates both:** greedy gives the number you'd actually *ship* (the low-latency
  path); modified-beam gives the accuracy *ceiling* of the same trained model. The gap tells you
  whether beam is worth its extra latency for live calls. Bookbot's own numbers make this concrete:
  CV-es **greedy 2.85** vs **modified-beam 2.71** — only ~0.14 absolute for materially more compute,
  which itself is the answer: for this architecture/data, greedy is fine and you lose almost nothing
  by taking the low-latency path. Measuring both on *your* model confirms that holds (or flags if
  beam suddenly matters, e.g. on telephone-band audio where the acoustic model is less certain and
  the beam may recover more).

❯ explain this: Low-LR encoder finetune + normal-LR decoder/joiner.

● It's a differential (per-component) learning-rate strategy, and it's the specific mechanism that
  makes the warm-start actually pay off. Tie it to the three parts of an RNN-T transducer:

  - **Encoder (Zipformer)** — the big acoustic model, audio features → acoustic embeddings.
  Vocabulary-agnostic (it never sees text). In bookbot's epoch-80 checkpoint this is *already a
  fully-converged Spanish acoustic encoder* (~80 epochs on CV-es + SLR72). This is the expensive
  asset you're reusing.
  - **Decoder (prediction network)** — small autoregressive net over *previously emitted tokens*.
  Its embedding table is tied to the vocabulary.
  - **Joiner** — combines encoder + decoder outputs into a distribution over the vocabulary; its
  output layer's width *is* the vocab size.

  **Why this asymmetry is forced on you:** you're changing the vocabulary — bookbot's 37 IPA
  phonemes → a ~500–1000-token BPE/word vocab. The decoder's token embeddings and the joiner's
  output projection are vocab-shaped, so they **cannot be reused — they must be reinitialized
  randomly**. The encoder, being text-blind, transfers as-is. So right after weight surgery you have
  a near-perfect encoder bolted to two randomly-initialized (garbage-output) heads.

  **The failure mode if you train all three at the same LR:** the random decoder/joiner emit
  nonsense, producing large, noisy gradients. At a normal LR those gradients backpropagate into the
  pristine encoder and **catastrophically overwrite the converged Spanish acoustic representations**
  before the heads have learned anything — you've effectively thrown away the warm-start and are now
  training from scratch, but worse (corrupted init).

  **The fix:**
  - **Decoder + joiner → normal LR:** they're random and must learn fast from zero — give them the
  full learning rate.
  - **Encoder → low LR** (often: *freeze* for an initial warmup, then unfreeze at ~10–100× smaller
  LR): you want to *preserve* its knowledge and only gently adapt it — to the new emission
  granularity (BPE/word targets align differently in time than phonemes), to data bookbot didn't see
  (MLS), and to the telephone-band augmentation. "Low," not "zero," because some adaptation is
  needed; the freeze→low-LR-unfreeze schedule lets the heads stabilize first so they stop sending
  destructive gradients into the encoder.

  This is the standard pretrained-backbone + fresh-head transfer recipe. In icefall it's parameter
  groups with per-group LR (and/or an encoder-freeze for K steps then unfreeze with an LR scale),
  plus the usual warmup schedule.

  **Why it's in the plan's critical path:** done right, this is exactly what collapses single-3090
  training from ~weeks (from-scratch) to ~days — you only fully train two small modules and lightly
  nudge the big one. Done wrong (uniform LR), you get *both* no speedup *and* a model potentially
  worse than from-scratch. That fragility is precisely why the plan keeps a from-scratch fallback:
  if the surgery + differential-LR tuning proves finicky, you drop back to the known-good full run
  rather than chase it.

❯ could we just fine-tune this model to output IPA and insert spaces?

● Yes — and that's genuinely the sharpest idea in this whole thread. It's a real third option, and
  for a *first* attempt it has the best risk/reward of the three. But be precise about what it does
  and doesn't buy you.

  ## Why it's much cheaper than the BPE-retrain plan

  You're adding **one token** (a word-boundary `▁`) to the 37-token vocabulary, not swapping the
  vocabulary. That changes the warm-start math entirely:

  - Decoder embedding table: 37 → 38 rows — **append one randomly-init row, keep the other 37**.
  - Joiner output layer: 37 → 38 — **append one output unit, keep the rest**.
  - Encoder: unchanged (same phonemes, text-blind).

  So ~37/38 of the head weights survive intact and the encoder is fully preserved. The
  catastrophic-forgetting risk that forced the careful differential-LR dance in the BPE plan is
  *largely gone* — the task is almost identical to what the model already does, plus one new symbol.
  This is a **light fine-tune, plausibly hours-to-days on the single 3090**, not the multi-day
  decoder/joiner-from-scratch run.

  And the data side is trivial: bookbot trained on **gruut-phonemized** transcripts, and gruut
  phonemizes word-by-word. So you regenerate the *same* training transcripts with a boundary token
  inserted between words — no new audio, no Whisper, no MLS ingest. Just re-run gruut on text you
  already have, joined with `▁`.

  ## What it solves — and what it doesn't

  It solves the **hard half** of the IPA→text problem. Segmenting a 175-character continuous phoneme
  run is the nasty part; getting the model to emit boundaries reduces post-processing to **per-word
  IPA→grapheme lookup**, which is tractable: build a reverse lexicon by running a big Spanish
  wordlist through gruut (grapheme→phoneme), invert it (phoneme-string → word[s]), disambiguate
  collisions with a small frequency/LM. A few days of well-defined engineering.

  It does **not** eliminate the converter. You still need that IPA→spelling step, and Spanish
  spelling carries information IPA discards: b vs v (both /b/), the Castilian c/z/s split, silent h,
  j vs g, y/ll, and **written accents are gone entirely**. A per-word lexicon + LM handles most of
  this but it's lossy on exactly those cases.

  It also adds a **new ceiling: connected-speech boundary accuracy.** Spanish word boundaries are
  frequently *not* acoustically present — "los hombres" is realized [lo‿so m b ɾ e s], liaison and
  resyllabification erase the seam. The model would place boundaries partly from a learned
  phonotactic LM in the decoder, so it *will* misplace them at exactly the fast-speech junctures
  that matter — and a misplaced boundary then breaks the per-word lookup. That error mode doesn't
  exist in the BPE model.

  ## Honest three-way

  | | training cost (1×3090) | post-processing | quality ceiling |
  |---|---|---|---|
  | **A.** IPA as-is + external segmenter+converter | zero | hardest (segment *and* map) | low —
  segmentation on raw phoneme run is brittle |
  | **B.** Fine-tune: add boundary token (your idea) | **low (hrs–days)** | medium (per-word
  lexicon) | medium — capped by boundary errors + lossy IPA→spelling |
  | **C.** BPE-retrain warm-started (the plan) | high (days–wks) | **none** | **highest** — model
  learns real orthography (b/v, accents) jointly from data |

  (C) wins on end quality because graphemes carry strictly more information than phonemes and a BPE
  model learns the disambiguating lexicon/LM *optimally from data* instead of you bolting on a
  weaker external one. But (B) is the **cheapest experiment that tells you the most**: if the
  boundary fine-tune + a gruut-reverse lexicon yields readable Spanish, you may never need (C); if
  boundary placement is too sloppy on connected speech, that's exactly the evidence that justifies
  paying for (C).

  My recommendation: **do (B) first as the de-risking probe.** It's a small, warm-start-preserving
  fine-tune on re-phonemized transcripts plus a bounded lexicon-building task — days, not weeks —
  and it directly answers the open question ("how good would streaming Spanish text actually be from
  this acoustic model?") at a fraction of (C)'s cost. Keep (C) as the upgrade path if the
  boundary/converter ceiling proves too low for phone calls.

  There are two different things that get conflated:

  - **Multilingual** = the model *covers* both languages, but effectively one at a time (you feed it
  Spanish, it does Spanish; English, it does English).
  - **Dual-language / code-switching** = the model handles both *mixed within a single stream*, the
  way real bilingual phone calls actually sound ("…sí, but the thing is que no llegó el invoice…").

  Everything we evaluated was judged on the first. On the second, here's the honest map:

  - **Voxtral** — multilingual (13 langs incl. en+es), streaming, grapheme. It's the *closest thing
  we have* to a dual-language streaming model: one model spanning both, already stood up. **But its
  code-switch behavior is completely untested by us** — we only ran it on clean monolingual Spanish.
  Multilingual ≠ code-switch-robust.
  - **parakeet-tdt-0.6b-v3** — multilingual, but we *watched it thrash*: it auto-detects per chunk
  and "flips" to English on ambiguous Spanish ("El El", language bleed). That's the cautionary
  evidence — auto-detect multilingual models tend to oscillate exactly on mixed input.
  - **Whisper** — the opposite failure: you pin one language and it *transliterates* the other (the
  report found `--lang es` turning English into Spanish-looking nonsense). Forcing a language is
  wrong for a bilingual call by construction.
  - **bookbot zipformer, Vosk, NVIDIA streaming, Kyutai** — monolingual or English-only. Not in the
  running for this at all.

  And the deeper truth: **code-switch streaming ASR is a genuinely hard, under-served problem in the
  field** — not just "we didn't look." Dedicated code-switch models tend to be
  language-pair-specific research artifacts (the well-studied ones are Mandarin-English); a robust
  general EN↔ES code-switching *streaming* model isn't an off-the-shelf solved thing.

  ### Step 1 — kick off session-ID detection (background)

  The session ID isn't an env var. Detection works by emitting a
  random marker, waiting for it to flush to a `.jsonl` file, then
  grepping the session directories to find the match. The flush takes
  a few seconds, so do it in background.

  Subagents log to a different place than top-level sessions, and the
  poller must hit the location Claude Code writes **in real time**
  (while this skill is still running inside the subagent), not a
  backup copy that only appears after the subagent exits:

  - **Top-level sessions** flush to
    `~/.claude/projects/<bucket>/<UUID>.jsonl` (depth 2 under
    `~/.claude/projects/`). The ID is the basename.
  - **Task-runner subagents** flush, in real time, to
    `~/.claude/projects/<bucket>/<parent>/subagents/agent-<aid>.jsonl`
    (depth 4 under `~/.claude/projects/`). The ID is the composite
    `<parent>-<aid>`. Note the `<parent>` directory is *above*
    `subagents/`. A backup hardlink at
    `~/project/sessions/subagents/<parent>/agent-<aid>.jsonl` is
    created by `task_runner.py --complete` — but that runs only
    *after* the subagent exits, so it does **not** exist yet while
    `end` is running. The poller must therefore search the live
    `~/.claude/projects/` tree, not the backup tree.

  ```bash
  # Foreground: emit marker
  marker="SID_$(openssl rand -hex 8)"; echo "$marker"
  ```

  Then launch the poller via Bash with `run_in_background: true`
  (replacing `<MARKER>` with the value just emitted):

  ```bash
  until path=$( { \
          find ~/.claude/projects/ -maxdepth 4 -name '*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
          find ~/project/sessions/subagents/ -maxdepth 2 -name 'agent-*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
        } | head -1); \
        [ -n "$path" ]; do sleep 2; done
  # Translate path to session ID. Three possible shapes:
  #   ~/.claude/projects/<bucket>/<parent>/subagents/agent-<aid>.jsonl  (live subagent — parent
  ABOVE subagents/)
  #   ~/project/sessions/subagents/<parent>/agent-<aid>.jsonl           (post-complete backup —
  parent BELOW subagents/)
  #   ~/.claude/projects/<bucket>/<UUID>.jsonl                          (top-level session)
  case "$path" in
    */subagents/agent-*.jsonl)            # live subagent: <parent>/subagents/agent-<aid>.jsonl
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      parent=$(basename "$(dirname "$(dirname "$path")")")
      echo "${parent}-${aid}" ;;
    */subagents/*/agent-*.jsonl)          # backup hardlink: subagents/<parent>/agent-<aid>.jsonl
      parent=$(basename "$(dirname "$path")")
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      echo "${parent}-${aid}" ;;
    *) basename "$path" .jsonl ;;
  esac
  ```

  The bash run ID lets you check the output later via `BashOutput`.

  **Why this layout matters.** The marker the subagent emits is
  written only to the subagent's own JSONL — the live one under
  `~/.claude/projects/<bucket>/<parent>/subagents/`, four levels deep.
  An earlier version of this poller capped the first `find` at
  `-maxdepth 2` (so it never reached depth-4 subagent files) and
  relied on the second `find` over `~/project/sessions/subagents/`
  for subagents. But that backup tree is populated by
  `--complete` *after* the subagent exits, so during the `end` run it
  is empty: the poller timed out and the agent fell back to "find the
  recently-touched top-level JSONL" — which yielded the *parent
  session's* UUID, not the subagent's own identity, collapsing
  multiple subagents under one parent into the same compaction
  filename. Searching `~/.claude/projects/` to `-maxdepth 4` reaches
  the live subagent JSONL and yields the correct composite ID, giving
  each subagent its own compaction. The two `case` arms disambiguate
  the live layout (`<parent>/subagents/agent-*.jsonl`, parent above)
  from the backup layout (`subagents/<parent>/agent-*.jsonl`, parent
  below); the backup `find` is kept as a harmless fallback for re-runs
  that happen after `--complete`.
