❯ you find a bug in vLLM?

● Sort of — we confirmed a crash that's at least bad behavior in vLLM, but didn't file it upstream.
  We worked around it.

  **What it is.** vLLM's `--max-model-len` is supposed to be a sequence-length cap, but hitting it
  doesn't end the sequence cleanly. The decode produces one token *past* the limit, then
  `_bookkeeping_sync` in `vllm/v1/worker/gpu_model_runner.py` fires an `AssertionError`:

  ```
  Sampled token IDs exceed the max model length.
  Total number of tokens: 16385 > max_model_len: 16384
  ```

  That assertion **kills the entire EngineCore**, not just the offending sequence. APIServer then
  shuts down cleanly. From the client side: WS closes with no error frame, `:8000/health` returns
  000, GPU goes idle, needs full `systemctl restart`. Confirmed live on 2026-05-19 21:28.

  **Why it's a bug (not just a config issue).** The limit should be enforced as a stop condition —
  sample-and-truncate, or refuse-to-sample, ending that sequence with a finish reason. Instead it's
  an `assert` that fires *one token over* and takes down the whole engine including any other
  concurrent sessions. Classic off-by-one-meets-fatal-assertion.

  **Pre-crash tell.** Throughput halves (~21 → ~11–14 tok/s) as sequence grows — that's just
  O(n)-per-token attention with no rolling window, not memory pressure (KV cache stayed at 31.8%).
  So the crash is preceded by a noticeable lag buildup if you're watching.

  **What we did about it.** Worked around it from the client: Silero-VAD-driven per-stream WS
  auto-recycle (`9a361ee` in `~/asr`) — each phone-call side recycles at natural silences (≥800 ms),
  so the cap is effectively unreachable. Backstop force-recycles at 1100 s if someone genuinely
  never pauses.

  We did *not* file an upstream issue. Want me to put one together? The repro is small (run
  `Voxtral-Mini-4B-Realtime` with a tiny `--max-model-len`, feed it long enough audio).

  **PR #38483** by `machov` — open since 2026-03-29 (~7 weeks, no human review yet,
  `REVIEW_REQUIRED`).

  **The diff** (`gpu_model_runner.py`): replaces the assertion with an if-branch that:
  1. Adds `req_idx` to `invalid_req_indices` (and the async set when async scheduling is on).
  2. For the sync path, calls `valid_sampled_token_ids[req_idx].clear()`.
  3. `continue`s past bookkeeping for that request.

  PR author's claim: "scheduler infrastructure already handles `FINISHED_LENGTH_CAPPED` which maps
  to `FinishReason.LENGTH`, so this change integrates seamlessly."

  **The hole** — the `gemini-code-assist` bot flagged it on day one and the comment hasn't been
  addressed:

  > the current implementation causes requests to hang indefinitely because the scheduler never
  receives the final tokens needed to trigger a completion status. It is recommended to truncate the
  sampled tokens to fit the limit rather than clearing them, ensuring the request finishes
  gracefully.

  That looks right to me. The `FINISHED_LENGTH_CAPPED` path in vLLM fires when a request *sees* its
  `num_tokens` cross `max_model_len` after a sampled token is appended — but this patch never
  appends the overflow token (it clears it for sync, doesn't write it at all in either branch). So
  the request lingers in the batch as "invalid" with no terminating token, no
  `finish_reason="length"` emitted to the client, and on the next step the same overflow condition
  recurs. From a `/v1/realtime` WS client's view: the engine no longer crashes, but the stream hangs
  and the WS never gets a clean close — arguably worse than the crash, since you don't even get a
  reconnect signal.

  The fix the bot suggests — **truncate** the sampled IDs to fit (`num_sampled_ids =
  self.max_model_len - start_idx`, write that prefix into the input batch as normal, let the
  existing finish-reason machinery do its job) — is the right shape. PR author hasn't responded.

  **Other concerns** in the PR as-submitted:
  - "Validated the fix logic with a simulation test" — no real-engine repro test, no test added to
  the suite.
  - The async branch *only* adds to the set, doesn't even clear tokens, so async behavior is
  inconsistent with sync (the bot's hang-forever critique applies equally to both, just by different
  mechanisms).
  - Doesn't address the deeper bug in #40302 / the #38428 follow-up comment: the *scheduler-side
  admission check* for multimodal placeholder insertion. Catching it at sample-time still wastes a
  step on a request that the scheduler shouldn't have batched in that shape.

  **Verdict.** A real fix in spirit (assert→graceful), but a buggy implementation that the
  maintainers correctly haven't merged. Our VAD-recycle workaround sidesteps both the crash and this
  PR's hang behavior, so we're fine to wait. Posting on #39996 with our independent repro is still
  worthwhile; piling onto #38483 to second the bot's truncate-not-clear point would also help
  unstick it.

  **PR #40072** by `ianliuy` — 159 add / 1 del across 2 files (`scheduler.py` + a new unit-test

  **Approach.** Where #38483 patched the *symptom* in `gpu_model_runner.py:_bookkeeping_sync`,
  #40072 patches the *cause* in `vllm/v1/core/sched/scheduler.py` — preventing the overflow request
  from being scheduled in the first place. Three layers:

  1. **`_handle_stopped_request`** — after `_update_request_as_session` extends a session with new
  streaming input, if `request.num_tokens >= max_model_len`, set `FINISHED_LENGTH_CAPPED` and
  return. Includes a logger.warning. This is the path that fires on every chunk continuation for a
  long-lived `/v1/realtime` session.
  2. **`add_request`** — same check when a `WAITING_FOR_STREAMING_REQ` session receives a new chunk;
  calls `finish_requests(..., FINISHED_LENGTH_CAPPED)` to remove cleanly.
  3. **WAITING scheduling loop** — adds the `min(num_new_tokens, max_model_len - 1 -
  num_computed_tokens)` clamp (mirroring the existing RUNNING-path guard at line 415–416 that the PR
  author correctly identifies as missing from the WAITING path), and replaces the bare `assert
  num_new_tokens > 0` with `if num_new_tokens <= 0: self.finish_requests(...); continue`.

  **Tests added.** Three real unit tests (not "simulation"):
  - `test_streaming_session_max_model_len_cap_via_handle_stopped`
  - `test_streaming_session_max_model_len_cap_via_add_request`
  - `test_streaming_session_length_capped_waiting_request_does_not_block_queue` — a direct
  regression for head-of-line blocking, including the assertion that `output.finished_req_ids ==
  {capped.request_id}` and the tail request still gets scheduled.

  **Gemini-bot review.** The bot flagged "using a break statement … causes head-of-line blocking."
  Looking at the current diff the author uses `continue` (not `break`) at the right point, *and*
  added the explicit HOL-no-blocking test. So either Gemini was reviewing an earlier revision or got
  confused — the concern is addressed in the current state.

  **Substantive critique I'd raise.** Two minor things, but they shouldn't be blockers:

  1. **Off-by-one in the `>=` check.** The two new guards use `request.num_tokens >=
  self.max_model_len`. The assertion that actually crashes is `end_idx <= self.max_model_len` (so a
  length of exactly `max_model_len` is legal). Finishing at `>=` may shave one token of legitimate
  capacity. The WAITING-loop clamp uses `max_model_len - 1 - num_computed_tokens`, so all three
  sites are consistent in being one-token conservative, but it's worth a note. (The assertion-side
  fix in #38483 would use `>`.)
  2. **No `logger.warning` on the WAITING-loop `finish_requests` path** — the other two sites log,
  this one doesn't. Cosmetic, but it means a silent "request finished length-capped" if it ever
  fires through the WAITING path instead of the streaming-update paths.

  **Verdict.** This is the structural fix the bug deserves — it identifies the actual missing guard
  (the WAITING path lost the RUNNING path's `max_model_len` clamp), patches all three scheduler
  entry points where a streaming session can grow past the cap, and ships regression tests including
  the HOL-blocking case. #38483 is patching the wrong layer; #40072 should be the one to land.

  ### Step 1 — kick off session-ID detection (background)

  The session ID isn't an env var. Detection works by emitting a
  random marker, waiting for it to flush to a `.jsonl` file, then
  grepping the session directories to find the match. The flush takes
  a few seconds, so do it in background.

  Subagents log to a different place than top-level sessions, and the
  poller must hit the location Claude Code writes **in real time**
  (while this skill is still running inside the subagent), not a
  backup copy that only appears after the subagent exits:

  - **Top-level sessions** flush to
    `~/.claude/projects/<bucket>/<UUID>.jsonl` (depth 2 under
    `~/.claude/projects/`). The ID is the basename.
  - **Task-runner subagents** flush, in real time, to
    `~/.claude/projects/<bucket>/<parent>/subagents/agent-<aid>.jsonl`
    (depth 4 under `~/.claude/projects/`). The ID is the composite
    `<parent>-<aid>`. Note the `<parent>` directory is *above*
    `subagents/`. A backup hardlink at
    `~/project/sessions/subagents/<parent>/agent-<aid>.jsonl` is
    created by `task_runner.py --complete` — but that runs only
    *after* the subagent exits, so it does **not** exist yet while
    `end` is running. The poller must therefore search the live
    `~/.claude/projects/` tree, not the backup tree.

  ```bash
  # Foreground: emit marker
  marker="SID_$(openssl rand -hex 8)"; echo "$marker"
  ```

  Then launch the poller via Bash with `run_in_background: true`
  (replacing `<MARKER>` with the value just emitted):

  ```bash
  until path=$( { \
          find ~/.claude/projects/ -maxdepth 4 -name '*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
          find ~/project/sessions/subagents/ -maxdepth 2 -name 'agent-*.jsonl' -mmin -2 \
               -exec grep -l "<MARKER>" {} + 2>/dev/null; \
        } | head -1); \
        [ -n "$path" ]; do sleep 2; done
  # Translate path to session ID. Three possible shapes:
  #   ~/.claude/projects/<bucket>/<parent>/subagents/agent-<aid>.jsonl  (live subagent — parent
  ABOVE subagents/)
  #   ~/project/sessions/subagents/<parent>/agent-<aid>.jsonl           (post-complete backup —
  parent BELOW subagents/)
  #   ~/.claude/projects/<bucket>/<UUID>.jsonl                          (top-level session)
  case "$path" in
    */subagents/agent-*.jsonl)            # live subagent: <parent>/subagents/agent-<aid>.jsonl
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      parent=$(basename "$(dirname "$(dirname "$path")")")
      echo "${parent}-${aid}" ;;
    */subagents/*/agent-*.jsonl)          # backup hardlink: subagents/<parent>/agent-<aid>.jsonl
      parent=$(basename "$(dirname "$path")")
      aid=$(basename "$path" .jsonl); aid=${aid#agent-}
      echo "${parent}-${aid}" ;;
    *) basename "$path" .jsonl ;;
  esac
  ```

  The bash run ID lets you check the output later via `BashOutput`.

  **Why this layout matters.** The marker the subagent emits is
  written only to the subagent's own JSONL — the live one under
  `~/.claude/projects/<bucket>/<parent>/subagents/`, four levels deep.
  An earlier version of this poller capped the first `find` at
  `-maxdepth 2` (so it never reached depth-4 subagent files) and
  relied on the second `find` over `~/project/sessions/subagents/`
  for subagents. But that backup tree is populated by
  `--complete` *after* the subagent exits, so during the `end` run it
  is empty: the poller timed out and the agent fell back to "find the
  recently-touched top-level JSONL" — which yielded the *parent
  session's* UUID, not the subagent's own identity, collapsing
  multiple subagents under one parent into the same compaction
  filename. Searching `~/.claude/projects/` to `-maxdepth 4` reaches
  the live subagent JSONL and yields the correct composite ID, giving
  each subagent its own compaction. The two `case` arms disambiguate
  the live layout (`<parent>/subagents/agent-*.jsonl`, parent above)
  from the backup layout (`subagents/<parent>/agent-*.jsonl`, parent
  below); the backup `find` is kept as a harmless fallback for re-runs
  that happen after `--complete`.
